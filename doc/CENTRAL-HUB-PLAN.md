#### MQL 探针结果与一个自我纠错

MT5 两个终端 **14/14 全过**，包括最关键的几条：

```
PASS  sendMore() accepted the topic frame
PASS  ...frame 1 is the v1 envelope, byte-identical
PASS  more() is TRUE on frame 0
PASS  more() is FALSE on the last frame
PASS  an unsubscribed prefix stops being delivered
```

**MT4 两个终端 13/14**，唯一失败的是 `an unsubscribed prefix stops being delivered`。
  
两边绑定的都是 **libzmq 4.2.1.0**（MT4 32 位 / MT5 64 位），版本不是原因。

> 注：当时两边绑的是 libzmq 4.2.1.0。后续已统一升级到 **libzmq 4.3.5**
> （含封包处理与内存溢出相关的多个 CVE 修复），两端仍然保持同版本 —— 这一点是 §14 的硬要求。

**原因在探针自己身上：unsubscribe 之后我用的是固定 `Sleep(400)`，那是个竞态。**
  
在较慢的 32 位 MT4 上，400ms 内退订还没落地就发布了，过滤器还是旧的，
  
于是"已退订"的消息仍然被投递 —— **探针把库给冤枉了。**

已改为**等待事件而不是等待时长**：XPUB 每收到一次订阅变更就发一条通知，
  
**通知到达本身就是"过滤器已更新"的信号**。

> **对设计的影响很小**：即使退订真的慢/失效，最坏后果是
>   
> **receiver 继续收到一个它已不再镜像的 sender 的流量**——
>   
> 而 SID 路由会把这些数据丢掉。**是浪费带宽，不是错误行为。**
>   
> 但这条必须留档：**它说明"退订生效"这件事不能靠猜时间**，
>   
> Phase 1 的 receiver 在 sender 列表变更后应当**验证**退订，而不是假定它生效。

**最重要的发现：mql-zmq 其实完整支持多帧，不需要给绑定打补丁。**

```cpp
Socket::sendMore(string msg)   // 带 SNDMORE 的中间帧
Socket::send(string msg)       // 最后一帧（不带 SNDMORE）
ZmqMsg::more()                 // == zmq_msg_more()
Socket::isReceiveMore(bool&)   // == ZMQ_RCVMORE
```

我在 v2 里写"`ZmqMsg` 没有 `getPart()`，所以多帧要靠 `more()` 循环"——
  
**只看了 `ZmqMsg.mqh` 和 `Socket::send()` 的重载，漏看了 `sendMore()`**。
  
结论不变（方案 B 可行），但**风险 R6 从"必须先验证"降级为"已基本排除"**，
  
且**不需要改 `patch-zmq.py`**。这正是 Phase 0 存在的意义：把一个"看起来要打补丁"
  
的假设，在写任何业务代码之前变成一个已核实的事实。

## 1. 两个部署层级（本版的核心定位）

```
┌──────────────────────────────────────────────────────────────┐
│  Tier 1 · Direct（网状）        —— 初级用户，默认，不改动        │
│                                                              │
│   一个 VPS，或全部跑在本地电脑。不需要跨网，不需要中枢。         │
│   和 MQL5 Market 上在售的 copier 一样：装两个 EA，填 IP:port。   │
│   ★ 本版对 Tier 1 的要求：零改动、零新概念、零新端口。           │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│  Tier 2 · Hub（星型）           —— 进阶用户，可选开启            │
│                                                              │
│   机器散在多个 VPS，网状管不动，走中央管理。                    │
│   ★ 只有填了 HubEndpoint 的 EA 才进入这个模式。                 │
│   ★ 没填 = 完全走 Tier 1，一行代码路径都不变。                  │
└──────────────────────────────────────────────────────────────┘
```

**这条定位决定了三个设计约束**，后面所有细节都服从它们：

1. **Tier 1 的线上格式一个字都不能改。** 已经跑起来的初级用户升级 EA 后必须照常工作。
     
   → 中央通道是**新协议（v2）**，只存在于 Tier 2 的链路上。
2. **中枢挂掉不能影响 Tier 1 用户。** 他们根本不连中枢，天然无关。
3. **同一个 EA 可以同时属于两层**（sender 就是：既有自己的直连端口，又连中枢）。
     
   所以"进不进 Tier 2"必须是**运行时由 input 决定**，不能是编译期分支。

## 2. 现状（保留，已核实的事实）

- sender **bind** XPUB（`EventsPort`）；receiver **connect** XSUB 到 N 个 sender。
- 信封：`V=1|SID=<id>|SSID=<session>|SEQ=<n>|TS=<server s>|MS=<monotonic ms>|T=<TYPE>|P=<payload>`
- `SID` 是路由键；receiver 对不认识的 SID **静默丢弃**。
- `SSID` 每次 `OnInit` 重生成 → **中枢必须原样透传**，否则每次中枢重启都会让所有 receiver 重新同步。
- 频率：`SNAP` 全量推送最短间隔 15s（`SnapshotSeconds`，按需补发另计）/ `HBT` 5s（`HeartbeatSeconds`）/ `STAT` 收据 1s（`SyncHeartbeatSeconds`）+ 摘要 5s + 详细列表与监控报告 60s；`PING` 每 10s（`CP_PING_MS`）/`PONG` 应答。
- 容量：`CP_MAX_SENDERS 16`、`CP_MAX_PEERS 16`、`CP_MAX_POSITIONS 2048`。
- 对端表以**账户号**为键（两端共用）。

### 2.1 两个对实施有决定性影响的新发现（本次勘察）

**发现 A：`CopierTransport` 已经同时持有两个 socket。**

```cpp
Socket *m_pub;   // sender: XPUB  —— BindSender()
Socket *m_sub;   // receiver: XSUB —— ConnectReceiver()
Send()        -> m_pub.send()      // 走直连通道
SendStatus()  -> m_sub.send()      // 走上行
Drain()       -> m_sub.recv()
DrainStatus() -> m_pub.recv()
```

sender 要"双通道广播"，需要的正是 **XPUB(bind) + XSUB(connect)** 这一对——
  
**传输层已经有了**。sender 侧只需：多调一次 `ConnectReceiver(指向中枢)`，
  
发数据时 `Send()`（直连）和 `SendStatus()`（上中枢）各调一次。
  
**这是本方案里最省事的一块，v1 计划里我把它想复杂了。**

**发现 B：mql-zmq 的 `recv()` 只能收单帧，但 `more()` 可用。**

```cpp
bool recv(ZmqMsg &msg,bool nowait=false) { return -1!=zmq_msg_recv(msg,m_ref,...); }  // 一次一帧
bool more() { return 1==zmq_msg_more(this); }                                          // ← 存在
```

`ZmqMsg` **没有** `getPart(i)`。所以多帧消息要靠 `more()` 循环手工拼。
  
→ **多帧可行，但不是零成本，且必须写探针测试验证**（§4.3）。

## 3. 中央通道架构

### 3.1 拓扑

```
                    ┌──────────────────────────────────────┐
                    │      Central Hub  (Rust)             │
                    │                                      │
   Sender A ────────┤  XPUB (bind :6000)                   │
   (Account 111111) │    ▲ 上行：sender 数据 / receiver ACK │
        │           │    │                                 │
        │ 直连       │    ▼ 下行：sender 数据 / 中枢控制指令  │
        │ (Tier 1)  │                                      │
        ▼           │  + HTTP/WS :8080  + SQLite           │
   Receiver X       └──────────────────────────────────────┘
   (直连，不走中枢)              ▲            ▲
                                │            │
                    Receiver Y ─┘            └─ Sender B
                    (Account 222222)            (Account 333333)
```

**一个 XPUB 就够**，与你的描述一致（"Rust 作为 XPUB 发布者，所有 EA 订阅它"）。
  
所有 EA（sender 与 receiver）都 **XSUB connect** 到同一个端点。

**为什么一个 socket 够用**：ZMQ 的订阅过滤在**发送方向**生效——
  
中枢发布什么，只有订阅了对应前缀的 EA 才收得到。所以 sender 不会被别人的数据打扰，
  
receiver 也不会收到别人账号的控制指令。**前提是主题命名有纪律（§4.4）。**

**上行不需要订阅**：XPUB 会把所有 XSUB 对端发来的消息**全部**交给应用层，
  
不受订阅影响。所以中枢天然能收到全部上行数据，不需要额外配置。

### 3.2 中枢是"两帧转发器"，不是"重编码器"

中央通道的消息格式（**两帧**）：

```
Frame 0: <topic>                              ← 路由键，只有中枢和订阅方关心
Frame 1: V=1|SID=...|SSID=...|SEQ=...|...|P=... ← v1 信封，原样
```

中枢对 **Frame 1 一个字节都不碰**，只决定 Frame 0。这保住了 v1 的核心原则：

- 不重新实现分隔符转义、数字格式化、字段顺序 → **不可能静默改变一条交易指令**
- `SEQ` 顺序、`SSID` 语义自动保留 → 中枢对收敛完全透明
- 中枢重启不产生新 `SSID` → receiver 不会误判 sender 重启

**中枢额外解析一份用于监控**（持仓/权益/延迟），但那份是只读副本，不参与转发。

### 3.3 数据流

```
Sender 数据上行   Sender --XSUB--> Hub XPUB --[topic=<sender account>]--> 订阅了它的 Receiver
中枢控制下行      Hub    --XPUB--> Receiver/Sender (topic=@<target account>)
Receiver ACK 上行 Receiver --XSUB--> Hub XPUB (topic=@hub) --> 中枢消费，不再转发
```

**`STAT` 的处置（D13 已定）**：Tier 2 下 `STAT` **由中枢消费，不再下发给 sender**。

- 理由：中枢本来就要拿这些数据做监控；而且 `STAT` 的语义是"这个 receiver 现在怎么样"，
    
  在中央模式下**属于中枢的视图，不属于某个 sender**
- sender 面板因此不再显示 receiver 状态行——**改为显示"中枢连接状态"**（D14，见 §8.3）
- 操作员要看 receiver 状态：**网页前端**

#### D13 的细化：快照投递收据走 `RCPT`（2026-10-13 实测后追加）

实测发现：D13 让 `STAT` 停在中枢，**顺带把「快照投递收据」也一起拦死了** ——
而收据搭的就是 `STAT` 的车（完整证据链见 `doc/SNAPSHOT-DEMAND-PLAN.md` §1.4）。

**收据不是「receiver 状态」。** 它是「我发出去的那份快照，你手上是不是这一份」——
一个**投递信号**，只有 sender 能据此行动，其他任何节点都观察不到。所以：

- 中枢**继续消费** `STAT`，**监控数字（EQ/BL/HELD/LOTS/RISK…）仍然只留在中枢**（D13 不变）
- 中枢**只抽出** `LOGIN` / `SID` / `H` 三个字段，以**新的消息类型 `RCPT`**
  单播回 `@<SID>` —— 复用**已经存在**的 hub → node 控制通道（`PONG`/`WHO` 同一条）
- **不新增主题命名空间、不引入第二套身份**：sender 启动时订阅的 `@<nid>`，
  正是 receiver 在 ini 里写的 `id=`

**这是 D13 的细化，不是例外。** D13 管的是「状态属于谁」；`RCPT` 放行的是「投递到没到」。

配套（同一轮实现）：

- `hub/src/main.rs` 新增 `send_receipt()`；`Stats` 新增 `receipts` 计数器
  （中枢**自己发起**的消息，`forwarded`/`control`/`dropped` 都看不见它 ——
  而「中枢静默地做了事」正是本项目反复踩的坑）
- `CopierDefs.mqh` 新增 `CP_T_RCPT`
- `CopierSender.mq4`：在 `DrainFrames`（中央通道下行）里处理 `RCPT`；
  并新增 `SenderAnswersTo(id)` —— **sender 要认两个 id**：
  直连 receiver 用**端口**称呼它，中央 receiver 用**账号（NID）**称呼它。
  只认端口会让中央模式的收据全部被丢弃（实测踩到的第二个坑）
- 验证：`tools/hub_stat_path_test.py` **15/15**；`bash hub/build.sh --test` **23/23**

## 4. 中央通道的寻址

### 4.1 为什么"直接指定收信人"在当前格式下做不到

你说："我们是用 ZMQ 的 XPUB/XSUB 结构，可以指定收信人。"

**ZMQ 的 pub/sub 确实能定向投递，但过滤的是"消息的起始字节"。**
  
订阅 `\x01` + 前缀 P，只有**以 P 开头**的消息才会被投递。

而现在的信封是：

```
V=1|SID=888888|SSID=...|SEQ=...
```

**每条消息都以 `V=1|` 开头**，没有任何消息以 `888888` 开头。
  
所以：

```cpp
sub.send("\x01" + "888888");   // 订阅 888888 的消息
// → 收不到任何东西。因为所有消息的第一个字节都是 'V'。
```

也就是说：**不是 ZMQ 不支持定向，而是我们的信封没有把路由键放在开头。**
  
这是 v1 为了让 MQL 解析简单而做的取舍，代价就是现在无法做网络层过滤。

> **现状（2026-10-13）**：上面这段是**引入 topic 帧之前**的历史背景，问题已经解决。
> 中枢模式现在是**两帧** `[topic, envelope]`，路由键就是第一帧，所以定向投递可用。
>
> 但**谁能用哪个主题**有一条硬规则，实现切片 B 时踩过：
> - `@<nid>` / `@all` —— **只有中枢能发起**。节点往这里发会被中枢当控制消息**消费掉、不转发**
> - `<nid>`（无 `@`）—— **数据主题**，中枢按前缀逐字节转发
>
> 所以 sender 要定向给某一个 receiver，用的是**那个 receiver 自己的 NID 作为数据主题**
> （receiver 相应订阅自己的 NID），**不是** `@<nid>`。
> 详见 `doc/PROTOCOL.md` 的「Addressing on the central channel」一节，
> 以及 `doc/SNAPSHOT-DEMAND-PLAN.md` §1.2（那里更正了一个错误结论）。

### 4.2 方案对比与决定

|       | 方案 A：载荷内过滤                                         | 方案 B：主题帧 + 订阅过滤                   |
| ----- | -------------------------------------------------- | --------------------------------- |
| 做法    | 所有 EA 订阅全部（`\x01`），每条消息都解码，看 `TO=<account>` 不是自己就丢 | 消息变两帧，Frame 0 = 主题；每个 EA 只订阅自己的主题 |
| 改动    | **零格式改动**                                          | 中央通道加一帧（**只影响 Tier 2**，Tier 1 不动） |
| 带宽    | 每个 receiver 收到**所有** sender 的全部数据                  | 只收到自己要的 sender 的数据                |
| 隐私    | 所有 receiver 能看到所有控制指令（含别人的配置变更）                    | 别人的控制指令根本不会投递给你                   |
| 扩展性   | 50 个 sender 时，每个 receiver 都在收 50 份流量               | 与订阅数量成正比                          |
| MQL 侧 | 无改动                                                | 需要 `more()` 循环收两帧（发现 B）           |
| 兼容性   | 与 v1 完全一致                                          | **只在中央通道**用，Tier 1 不受影响           |

#### ✅ 已决定：方案 B（主题帧 + 订阅过滤）

理由：

1. **它才是你说的"可以指定收信人"**——方案 A 严格说是"广播给所有人，然后各自假装没看见"。
2. **隐私是实质差别**。方案 A 下，A 用户的 receiver 能看到 B 用户的配置变更指令
     
   （即使它不执行）。这是不必要的暴露。
3. **带宽在进阶用户场景下是真问题**——他们的机器散在多个 VPS，流量是要花钱的。
4. **代价被限制在 Tier 2**。Tier 1 的线上格式一个字不改，初级用户完全无感。

方案 A 保留在文档里只作为**降级预案**：万一 Phase 0 的探针测试发现多帧在 mql-zmq 上
  
不可靠（§21-R6），就退回 A，代价是上面第 2、3 条。

### 4.3 方案 B 的落地细节

**帧格式**：两帧。ZMQ 的订阅匹配**只看第一帧**，这是标准做法。

**为什么不用"单帧前缀"**（`888888|V=1|...`）：那样 receiver 必须先剥前缀再解析，
  
多一处解析分支；而两帧让 Frame 1 与直连通道**逐字节相同**，
  
同一份解析代码两条链路共用。

**MQL 侧的实现方式**（已核实，不需要打补丁）：

```cpp
// 发送
pub.sendMore(topic);        // 带 SNDMORE 的中间帧
pub.send(envelope);         // 最后一帧

// 接收
ZmqMsg m0; sub.recv(m0,true);
bool more = m0.more();      // 必须在收下一帧之前读 —— RCVMORE 描述的是刚收到的这条
ZmqMsg m1; sub.recv(m1,true);
```

> `more()` 的读取顺序是**测试的一部分**，不是细节：RCVMORE 描述的是**刚投递的那条消息**，
>   
> 在收下一帧之后才读，读到的是下一条的状态。

**已完成的验证**（§0.2）：

- ✅ pyzmq 侧 11/11 PASS —— 主题帧、帧 0 过滤、多前缀、`@` 命名空间、取消订阅全部成立
- ✅ mql-zmq 侧 API 存在且无需补丁（`sendMore` / `more` / `isReceiveMore`）
- ⬜ 待终端实跑：`src/Scripts/CopierZmqProbe.mq4`（自包含，拖到图表即可）


> 这个代码库有一条硬规矩：**"One-way protocol does not mean one-way socket" 是量出来的，
>   
> 不是推出来的。** 主题帧同理——两个探针都留在仓库里，`zmq_topic_test.py` 已经跑通。

### 4.4 主题命名规范

```
<account>        数据：来自账号 <account> 的 sender
@<account>       控制：发给账号 <account> 的节点（sender 或 receiver）
@hub             上行：发给中枢的（ACK / REG / 请求）
@all             广播：中枢要求全员重新注册等
```

- `@` 前缀把"数据"和"控制"分到两个不重叠的命名空间。
    
  **这很重要**：没有它，一个 sender 的账号是 `888888`，而另一个节点的账号恰好
    
  以 `888888` 开头（如 `8888881`），订阅 `888888` 就会**同时收到两者**——
    
  ZMQ 是前缀匹配，不是精确匹配。
- 账号长度不一致时，前缀匹配仍会误伤。所以规范是：**控制一律带 `@`，
    
  数据一律纯数字，且订阅时用 `@` 区分。** 数据侧的账号前缀碰撞在
    
  账号等长（通常都是 8 位）时不会发生；§6 会给出更稳的兜底。

## 5. 协议 v2（仅中央通道）

### 5.1 兼容性原则

1. **Tier 1 的 v1 报文永远有效**，一字不改。
2. v2 只**新增** `T`，不修改任何现有 `T` 的载荷。
3. 未知 `T` **静默忽略**（现有代码已如此）→ 新旧节点可任意顺序升级。
4. 未填 `HubEndpoint` 的 EA 走 v1 路径，**不解析两帧，不订阅主题**。

### 5.2 新增消息类型

| T      | 方向       | 主题       | 载荷                                                            | 说明                            |
| ------ | -------- | -------- | ------------------------------------------------------------- | ----------------------------- |
| `REG`  | node→hub | `@hub`   | `ROLE=sender\|receiver;ACC=888888;VER=2.0;NAME=MT5-A;UP=1234` | 上线注册；中枢重启后靠它重建注册表             |
| `HBT2` | node→hub | `@hub`   | `ROLE=..;ACC=..;VER=..;NAME=..;UP=..`                         | 心跳扩展（**不改 `HBT`**，避免破坏 v1 解析）。`NAME` 于 2026-10-13 补上，见下 |
| `CFG`  | hub→node | `@<acc>` | `ID=AA2026;REV=12;INI=<整份 ini 文本>`                            | 配置下发                          |
| `ACK`  | node→hub | `@hub`   | `ID=AA2026;OK=1;REV=12` 或 `ID=AA2026;OK=0;ERR=...`            | 命令结果                          |
| `CFGR` | node→hub | `@hub`   | `REQ=1;ACC=..;REV=..`                                         | 节点请求重发配置（自愈 / 漂移修复）           |
| `WHO`  | hub→all  | `@all`   | `NONCE=..`                                                    | 要求全员重新注册                      |

> 你的 `CONFIG_UPDATE: {"account":888888,"changeiniID":"AA2026"}` 就是这里的 `CFG`，
>   
> 只是**用主题帧代替了 `account` 字段**——投递由 ZMQ 完成，不再需要"广播给所有人再各自过滤"。
>   
> `changeiniID` 原样保留，作为幂等键。

> **⚠️ `HBT2` 的 `NAME` 字段（2026-10-13 补上，推翻本节早先的一个决定）**
>
> `HBT2` **原先不带 `NAME`**，理由写在一份 selftest 里，而且是个好理由：
> 「一条有权报告名字的心跳，就有权报告**空**名字，而一个拿名字当真值的中枢
> 会因此抹掉 `REG` 建立起来名字」。
>
> **那条理由对「中枢怎么做」是对的，对「线上放什么」是错的。** 中枢现在的规则是
> **「空名字永不抹除」**（`hub/src/registry.rs` 的 `on_hbt`），所以那个危害在
> 它该被处理的地方被处理了 —— 名字于是可以跟着「存活证据」一起走。
>
> **旧设计的实际代价（实盘实测）**：只发心跳的节点**可见但匿名**。EA 早已挂载而
> **hub 重启**时，`g_announceCount` 早已越过 `CP_REG_REPEATS`，于是只发 `HBT2`，
> Name 列要等 hub 的 WHO 清扫触发重新 `REG` —— **约 10–15 秒的空白行**。
>
> **双向向后兼容**，这也是能安全改的原因：
> - 新 EA + 旧 hub：旧 hub 忽略不认识的键（它的 `routine` 名单只看 `T=`，载荷只取自己要的）
> - 旧 EA + 新 hub：新 hub 读到空 `NAME` → **不抹**既有名字
> - 名字仍由 `CopierSanitize` 消毒（`;` `=` 全替换成 `_`）—— 它要进网页
>
> 相关断言：`CopierSelfTest.mq4`（消毒 + 不会注入字段）、`hub/src/registry.rs`
> （空名字不抹 / 心跳即命名 / 改名跟随）、`tools/hub_api_test.py` 第 5 节。

### 5.3 为什么用 `HBT2` 而不是扩展 `HBT`

`HBT` 是 sender→receiver 的 1 秒高频报文。给它加字段，**旧 receiver 的解析可能错位**
  
（它按 `;` 切 `k=v`，多一个键通常无害，但少一个键有害）。新增一个 `T` 的成本接近零，
  
风险完全消除。**新功能一律走新 `T`，这是 v1 就定下的规矩。**

### 5.4 命令 / 确认语义

```
Hub                                    Receiver 222222
 │  [@222222] CFG ID=AA2026 REV=12 INI=...   │
 ├──────────────────────────────────────────►│
 │                                           │ 校验 → 应用 → 落盘
 │  [@hub] ACK ID=AA2026 OK=1 REV=12         │
 │◄──────────────────────────────────────────┤
```

规则：

`CMD`（操作命令，M5）走**同一套**机制：同样的 `202 + command_id`、同样的重试阶梯、同样的
`ACK` 处理，只是载荷是 `ID=..;OP=..[;ARGS=..]` 而不是 `REV=..;INI=..`。`ACK` 对两者是同一帧，
中枢按 `ID` 找到对应命令后，把审计动作加 `config.*` 或 `command.*` 前缀。

1. **`ID` 全局唯一**（即你的 `changeiniID`，格式 `AA2026` 之类）。`CFG` 的 `ID` 由 `(node, rev)`
   派生（内容派生，重试/重发/第二个中枢都是同一条命令）；`CMD` 的 `ID` 由 `(node, op, seq)`
   派生（序列派生，每次下发都是新命令，**同一操作连发两次是两条命令**，不会塌缩成一条）。
   ——序列是**中枢本地**的；§11 主备复制未做之前，两个中枢会对同一意图产生不同 `ID`，这一点由
   §5.4 规则 2 在节点侧兜底，且四个操作本身幂等（`pause` 两次仍是 `pause`，第二次 `closeall` 无仓可平）。
2. **节点必须幂等**：重复 `ID` 直接重发上次的 `ACK`，不重复应用。
     
   ——这一条在 §11 的主备场景下**是必需的**，因为两个中枢可能都下发同一条。
3. **中枢重试**：未收到 `ACK` 按退避重试（2s→5s→15s→60s），上限后标记 `UNKNOWN` 并告警。
     
   沿用现有 `CopierBackoff` 的阶梯，**不无限重试**。
4. `ACK` 带 `REV`，中枢据此确认节点跑的是哪一版。
5. 所有命令有超时，状态对前端可见（`pending`/`acked`/`timeout`/`rejected`/`unknown`）。

## 6. 身份：Account Number 作 ID

采用你的方案：**所有 sender / receiver 用自己的 Account Number 作为 ID。**

### 6.1 但必须先定一条规则：账号不唯一怎么办

账号在"一个经纪商的一个账户"内唯一，但下面两种场景会碰撞：

| 场景                                         | 后果                               | 建议                                                                                                 |
| ------------------------------------------ | -------------------------------- | -------------------------------------------------------------------------------------------------- |
| **同一账户挂两个 receiver**（不同 magic，镜像不同 sender） | 两个节点 ID 相同 → 中枢的注册表互相覆盖，配置下发会发错人 | **禁止**，或 ID 写成 `<acc>-<magic>`。建议在启动时检测并**报错拒绝启动**，理由和现在"magic 重复就拒绝启动"一样                          |
| **sender 和 receiver 同账户**（回环测试，你自己就在用）     | 两者 ID 相同，但角色不同                   | 主题里带角色：数据 `@s:<acc>` 用 sender 的，控制 `@<acc>` 用 receiver 的；或 ID 写成 `sender:<acc>` / `receiver:<acc>` |

**✅ 已决定**：内部 ID 用 **`ROLE:ACC`**（如 `sender:111111`、`receiver:222222`），
  
主题里只出现账号（因为主题要短、要前缀友好），角色靠 `REG`/`HBT2` 的 `ROLE` 字段传达。
  
这样既满足"用账号作 ID"，又不会在回环测试时撞车。

> 上表第 1 行（同一账户挂两个 receiver）**仍待确认**，见 §23.2 第 4 条。

### 6.2 ✅ 已决定：10 位及以上账号确定性截断为 9 位

**背景**：MT5 的 magic 是 `ulong`，没问题；但 **MT4 的 `OrderSend` magic 是 32 位有符号
  
`int`**，上限 2 147 483 647。所以 8 位账号安全，**10 位账号会溢出**。

**规则**（一条纯函数，全局唯一）：

```
NID(acc) = (acc < 1_000_000_000) ? acc : acc % 1_000_000_000
```

- 9 位最大值 999 999 999 < 2 147 483 647 → **对 MT4 的 int 永远安全**
- 是**确定性纯函数** → 重启、重新下发 ini、两端重算，都得到同一个值。
    
  这正是你担心的那个问题（"统一这个规则……不怕重启的问题，因为 INI 不会改变"）
- 截断发生时**启动放 warning**（不拒绝启动），因为它是可预期的、稳定的

**这条规则用在每一个地方**：`SID`、主题、magic、ini 里的 `id=`、注册表的节点 ID。

#### 由它派生出的三个细节（需要你点头）

**细节 1 — 保留哪 9 位？** 建议用 `acc % 1e9`，即**保留后 9 位**。

> 理由：经纪商账号的前几位常常是**共享**的经纪商/类型前缀，后几位才是序号。
>   
> 保留后 9 位区分度更高。例：`1234567890` → `234567890`。
>   
> （保留前 9 位则 `1234567890` → `123456789`，把区分度最低的部分留下了。）

**细节 2 — 截断在哪一端算？** 建议 **EA 算，Hub 不重算**。

`REG` 同时带两个字段：`ACC=<完整账号>`（给人看、给 UI 显示）和 `NID=<截断后>`（给机器路由）。
  
Hub **只信任 `NID`，永不自己计算**。

> 理由：一条规则只留一份实现。如果 Hub 也实现一遍，两端就有分叉的可能——
>   
> 而分叉的后果恰恰是你最担心的：**magic 变了，下一次 ini 下发就跟着变**。
>   
> 附带好处：UI 能显示完整账号（人认得出来），而路由用截断值。

**细节 3 — 截断会碰撞，但不会静默串仓。**
  
`1234567890` 和 `1234567891` 都截断成 `234567890`。

> **现有的检查会自动抓住它**：`ReportMagicConfig()` 已经检测"两个 sender 用同一个 magic"，
>   
> 并拒绝启动（理由写在代码里：所有查找都按 magic 走，两者无法区分，会互相平仓）。
>   
> 所以这是**响亮失败**，不是静默串仓。
>   
> 唯一要做的是把那条报错文案补上"可能由账号截断导致"这一句。

## 7. 配置下发与持久化

### 7.1 你的设计（采纳）

- receiver 填了 `HubEndpoint` → **忽略 Input Box 的其他 input**（和原来 `ConfigFile` 的行为一致）
- 配置来自 **ini 文件**，路径固定（`MQL\Files\copier.ini`），由中枢推送更新
- **两边重启都不会丢配置**：ini 落在 receiver 本地磁盘上

### 7.2 落地流程

```
1. 网页改配置
2. Hub 生成 REV+1，写 config_revisions 表（含 diff、操作人、时间）
3. Hub 发 [@<acc>] CFG ID=.. REV=.. INI=<整份 ini>
4. Receiver:
   a. 解析 + 校验（见 §10 的 magic 策略）
   b. 原子写盘：copier.ini.tmp → 校验可解析 → 替换 copier.ini
   c. 重新加载配置（把 OnInit 里的 LoadConfig 抽成可重入函数）
   d. 回 [@hub] ACK ID=.. OK=1 REV=<n>
5. Hub 收 ACK → 更新状态；超时 → 重试 → 最终告警
```

**发整份 ini 而不是 diff**：diff 的合并逻辑会成为新的正确性来源；
  
整份 ini 让"中枢所见的配置"与"节点上的配置"是**同一个字节串**，可直接比对。
  
（代价：一个 receiver 的 ini 通常 < 4KB，远小于 `CP_MAX_MSG_LEN 262144`，无所谓。）

**先写 `.tmp` 再原子替换**：`copier.ini` 是节点的启动依赖，写一半断电 = 节点再也起不来。

### 7.3 重启后的自愈（这是"两边重启不丢配置"的关键）

```
Receiver 启动
  ├─ 读本地 copier.ini（可能落后）
  ├─ 连中枢，发 REG（带本地 REV）
  └─ Hub 比较：本地 REV < 中枢 REV  →  主动补发 CFG
                本地 REV = 中枢 REV  →  无事
                本地 REV > 中枢 REV  →  中枢告警（有人在节点上手工改过）
```

**中枢不在时 receiver 必须能独立工作**：用本地 ini 继续跑，不阻塞等待中枢。
  
这条很重要——否则中枢一挂，所有 receiver 全停，而它们本来是可以继续跟单的。

### 7.4 一个必须提前想清楚的问题：中枢是 ini 的"唯一真相源"

中枢既然负责生成 ini，那它就是**配置的唯一真相源**。这带来两个后果：

- 有人在节点上手工改了 ini → 下次中枢下发会**覆盖**它。要在 UI 上显示漂移告警，
    
  而不是静默覆盖。
- **主备场景下只能有一个中枢接受写入**（见 §11）。

## 8. Sender 侧改动

|      | 未填（Tier 1）                              | 填了（Tier 2）                                |

3. `Emit()` 里多一行——直连照旧 `Send()`，同时 `SendUp(NID,msg)`。

4. `OnTimer` 多 drain 一个 socket；启动时发一次 `REG`

| 账户 / 端口 / 快照频率        | ✅                                     | ✅ 保留                                                                               |
| 持仓数 / 总手数             | ✅                                     | ✅ 保留                                                                               |
| **`Channel`**         | `direct only   (NID would be 111111)` | `direct + central   NID 111111`                                                    |
| **Receiver 列表 + RTT** | ✅                                     | ✅ **保留**（直连 receiver 照常连、照常上报）                                                     |
| **Hub 行**             | —                                     | **新增**：`HUB  tcp://10.8.0.1:6000   12 ms round trip` / `DISCONNECTED (34s silent)` |

**实现上 hub 就是 `CopierPeerTable` 里的一个普通 peer**（固定名 `hub`），
  
所以它复用现成的行渲染、超时判定和 `PING`/`PONG` RTT——
  
唯一特殊处理是**显示成 `HUB <endpoint>` 而不是账户号**，
  
因为把它显示成一个 receiver 会让"Receivers connected: 2"看起来像两个接收方，
  
而其中一个是基础设施。

**RTT 必须真的量出来**：ZMQ 的 `connect()` 立刻成功，**不管对端有没有在听**，
  
所以没有回包的话面板会永远显示"connected"——一个对着不存在的 hub 的假绿。
  
因此原型中枢也要回 `PONG`（它唯一主动发出的消息，见 `PHASE1-DESIGN.md` §3）。

## 11. 主备（Master / Slave）

你的判断是对的：**"过几秒会全部信息都再发"，所以不怕丢消息。**
  
这个性质比你可能意识到的更强——它让主备**几乎不需要"切换"这个动作**。

### 11.1 关键洞察：重复投递本身就是无害的

如果 master 和 slave **都**把同一个 sender 的流原样转发下去（它们都是转发器，
  
`SSID`/`SEQ` 不变），那么：

- **数据侧**：receiver 现有的 `SEQ <= last_seq` 守卫会**自动丢掉重复的那一份**。
    
  `doc/PROTOCOL.md` 里那条幂等规则（`SID:SSID:SEQ`）在这里免费生效。
- **控制侧**：`ACK`/`CFG` 靠 `changeiniID` 幂等（§5.4 规则 2），重复下发不会应用两次。

**所以不需要 epoch、不需要"选举"、不需要保证只有一个 publisher。**
  
两个中枢同时发，结果和只发一个完全相同。

### ✅ 11.2 已决定：**"双活发布 + 静默即接管"**

```
EA 侧：ConnectReceiver 到 [master, slave] 两个端点     ← 现有 API 已支持端点数组，零改动
       两个都订阅，两个都收。重复由 SEQ / ID 幂等消化。

Hub 侧：slave 平时【不发布】（或发布也无所谓）
       slave 监听 master 的心跳，超过 N 秒没听到 → 开始发布
       master 恢复 → 它继续发布，两者并存，receiver 照样只生效一次
```

**为什么这比"切换"好**：

- EA 侧**完全不需要知道**谁是 master。没有角色、没有状态机、没有切换窗口。
- 不存在"切换瞬间丢消息"的窗口——因为根本没有切换动作。
- 分区（脑裂）不是故障，是**正常状态**：两边都发，receiver 各收一次，去重后一致。

**配置库的读写语义**（按 D2/D9 更新）

- 网页持有 **master / slave 两个地址**，先连 master，不通再试 slave
- master → slave **单向复制**配置库（SQLite 文件级复制 / litestream / 逻辑复制）
- slave 平时**只读**


#### ✅ 读路径完全成立

两份内容同步，**连哪个都一样**——你说的没问题，这部分是对的。

#### ⚠️ 但写路径有一个必须先解决的问题

```
master 挂
  → 前端连 slave → 在 slave 上改了配置（REV 12 → 13）   ← 你的要求：这时仍能改
  → master 恢复
  → master → slave 单向复制
  → master 的 REV 12 **覆盖** slave 的 REV 13
  → 刚才那次修改**静默消失**
```

**这不是理论问题**：只要"被复制的一方也接受写入"，单向复制就**必然**会覆盖它。
  
而"两个内容同步"这句话，**对读成立，对写不成立**——写会改变同步关系本身。

#### ✅ 已选定：(a) 世代号 + 角色互换

1. 配置库有一个单调递增的 `generation`；**只有 active 的 Hub 接受写入**，每次写 `generation++`
2. 两个 Hub 一接触就交换 `(generation, hub_id)`；**世代号大的成为 active**，平手时比 `hub_id`
3. 落后的那个变为 passive，**主动从 active 拉取配置**——复制方向跟着角色走，
     
   而不是固定 master→slave
4. 前端把写请求发到 passive 时，passive 回"我不是 active，去连另一个"，前端**用已有的两个地址重试**

于是：

| 情形                  | 结果                                                  |
| ------------------- | --------------------------------------------------- |
| 两个都活着，generation 相同 | 比 `hub_id` 定 active，**稳定不抖**                        |
| master 挂，前端改 slave  | slave 的 generation 增长 → **它成为 active**              |
| master 恢复           | 它 generation 低 → **变成 passive 并同步** → **角色互换，不丢数据** |
| 两边同时被写（分区）          | generation 大的一方胜出，输的一方同步过去；**最后一次写赢，不是静默丢**         |

**这套规则只有 4 条，比 Raft 简单两个数量级**，而它解决的是一个真实存在的覆盖问题。
  
代价只有一个：前端在写失败时**要重试另一个地址**（一行逻辑，你已经在 D9 里做了）。

> 如果连这个都不想加，还有一个更省的替代：**前端只允许写 master**，
>   
> slave 纯只读。代价就是"master 挂掉期间改不了配置"——**但至少不会静默丢数据**。
>   
> 两条路都行，**只有"slave 可写 + 单向复制"这一种组合是不行的。**

### 11.3 备选方案（供你比较）

| 方案                            | 优点                 | 缺点                                  |
| ----------------------------- | ------------------ | ----------------------------------- |
| **双活发布 + 静默接管**（推荐）           | EA 零改动；无切换窗口；分区不致命 | 配置库需要单向复制；流量翻倍（但流量本来就不大）            |
| 浮动 VIP（keepalived / 云 LB）     | EA 只填一个地址；语义最简单    | 需要控制网络层；跨 VPS 商通常做不到；VIP 漂移本身也有秒级窗口 |
| 真正的选主（Raft / etcd）            | 理论最完备              | 对"两个节点的冗余"来说复杂度严重过剩                 |
| 中枢前置一个 ZMQ 代理（`zmq_proxy`）做热备 | 对 EA 透明            | 代理本身又成了单点，等于没解决                     |

> **建议**：先用"双活发布"，把配置库单写这件事做扎实。
>   
> 等真的遇到问题再考虑 VIP。**Raft 在这个规模下不值得。**

| ZMQ     | **zmq**（libzmq 绑定）          | 必须与 EA 侧同一个 libzmq，否则 CURVE/HWM 行为可能不一致 |
| 序列化     | serde                       | **ZMQ 层不做结构体反序列化**，只切两帧（§3.2）           |
| 数据库     | sqlx + SQLite（默认）/ Postgres | 编译期校验 SQL                               |
| 日志      | tracing                     | 结构化                                     |
| OpenAPI | utoipa                      | 生成 spec → 前端类型（§17）                     |
| 多帧      | 原生支持                        | 中枢侧零成本，成本全在 MQL 侧                       |

**ZMQ 与 tokio 的桥接**（最容易踩的工程点）：ZMQ socket **不是 `Send`/`Sync`**，
  
绝不能直接在 tokio 任务里用。标准解法：

```
专用 OS 线程（同步，独占全部 ZMQ socket）
  ├─ zmq::Poller 同时轮询 XPUB + ctrl(inproc PAIR)
  ├─ ctrl 是唤醒通道：tokio 侧要发命令时写一条，Poller 立刻醒
  └─ → tokio::sync::broadcast → 所有 WS 客户端
```

- **绝不在 ZMQ 线程里 `await`**
- 单线程 ZMQ 还顺带保证了**每 sender 的 `SEQ` 顺序**（串行处理 → 串行转发）

## 15. 数据模型（SQLite，刻意很小）

**按 D8：中央端只存"重新启动后必须还在"的东西。运行状态一律不落库。**

> **实现方案收敛说明（2026-10-16）**：实际落地按 D8 极简原则采用了结构化文本与 JSONL 持久化（`users.json`, `config_revisions.jsonl`, `commands.jsonl`, `audit.jsonl`（10MB 带 gzip 压缩轮转），`alert_channels.json`），完全满足重启后状态不丢、原子更新、只追加不覆写的核心需求，且免去了在 Windows MinGW 环境下链接外部 SQLite 编译器的复杂性。下表原规划中的各表对应转化为上述专用文件。

这条界限值得说清楚，因为"状态"和"配置"很容易被混为一谈：

|                             | 存不存         | 为什么                                         |
| --------------------------- | ----------- | ------------------------------------------- |
| 持仓、权益、手数、RTT、心跳             | **不存**      | 随时能从 EA 实时拿到；存了只是给自己制造一致性问题                 |
| 历史曲线（权益/持仓时间序列）             | **不存**（第一版） | 用户要的是"现在怎么样"，不是"上周三怎么样"。真要就加一张按小时 rollup 的表 |
| 用户、角色、会话                    | **存**       | 重启后还得能登录                                    |
| 节点 token                    | **存**       | 重启后还得能校验                                    |
| **每个 receiver 的 ini 与 REV** | **存**       | **中枢是 ini 的唯一真相源**（§7.4），不存就没法下发、没法检测漂移     |
| 审计流水                        | **存**       | 追责用，必须永久                                    |
| 未解决告警                       | **存**       | 重启后不该忘掉                                     |
| 在途命令                        | **存**       | 重启后要知道哪些命令还没 ACK                            |

```sql
-- 用户与权限
users(id INTEGER PK, username TEXT UNIQUE, pass_hash TEXT,
      role TEXT,              -- admin | operator | viewer
      created_at INTEGER, disabled INTEGER DEFAULT 0)

-- 节点注册表（靠 REG / WHO 重建，不是权威）
nodes(id TEXT PK,             -- "sender:111111"  (ROLE:NID)
      role TEXT, acc_full INTEGER, nid INTEGER,
      name TEXT, ver TEXT,
      first_seen INTEGER, last_seen INTEGER)

-- 每节点 token（D5：白名单免 token，名单外必须带 token）
node_tokens(node_id TEXT PK, token_hash TEXT, note TEXT)

-- 配置：中枢是 ini 的唯一真相源
configs(node_id TEXT PK, ini TEXT, rev INTEGER, updated_at INTEGER, updated_by TEXT)
config_revisions(rev INTEGER PK, node_id TEXT, ts INTEGER, actor TEXT,
                 ini TEXT, diff TEXT, result TEXT, ack_at INTEGER)

-- 在途命令（= changeiniID）
commands(id TEXT PK, node_id TEXT, ts INTEGER, op TEXT, args TEXT,
         state TEXT, ack_at INTEGER, err TEXT)

-- 审计（append-only）
audit(ts INTEGER, actor TEXT, action TEXT, node_id TEXT,
      before TEXT, after TEXT, result TEXT)

-- 告警（只留未解决 + 近期已解决）
alerts(id INTEGER PK, ts INTEGER, node_id TEXT, rule TEXT,
       severity TEXT, message TEXT, resolved_at INTEGER)
```

> **⚠️ 现状（2026-10-14）：`audit` 目前落在 `audit.jsonl`，不是 SQLite。**
>
> 实测 `rusqlite(bundled)` 在本机构建失败 —— `libsqlite3-sys` 的 build script 报
> `ToolNotFound: failed to find "gcc.exe"`（`cc` 要无前缀的 `gcc.exe`，Rust GNU
> 工具链只给 `x86_64-w64-mingw32-gcc.exe`；而补上整个 MSYS2 `mingw64/bin` 会抢走
> Rust 的 `ld`/`gcc`，即 `hub/build.sh` 第 2 节记录的 `ld: cannot find crt2.o`）。
> SQLite 属于 **M11**（存储层）的活。
>
> **但审计需要的性质不是「引擎」，而是「只追加、永不重写」** —— 追加模式的文件比数据库
> 更直接地给出这一点（没有 `UPDATE` 可以被说服）。记录形状**就是下面这张 `audit` 表**，
> 将来导入 SQLite 只是「逐行读 + INSERT」。
>
> 三条性质各有测试：只追加（写前后比字节）、`seq` 单调**跨重启**（缺口可检出）、
> 写失败必须响亮。详见 `hub/README.md`「The audit log (M7)」。

**保留策略**：`audit` / `config_revisions` **永久**；`alerts` 已解决的保留 30 天；
  
`commands` 完成超过 7 天清理；其余是活数据。

**为什么 SQLite 够用**：写入只发生在**人操作时**（改配置、加用户），
  
以及每分钟一次的节点心跳更新。这是"每天几十次写"的量级，
  
**SQLite 的 WAL 模式处理起来毫无压力**，而且备份就是一个文件。

> 什么时候才需要 Postgres：出现**第二个同时写库的 Hub 实例**时。
>   
> 而 D2 的"配置世代号 + 角色互换"已经把同时写限制在"只有一个 active"，
>   
> 所以第一版不需要。真要上，`sqlx` 的抽象让迁移成本可控。

### 17.2 账户与权限管理（D10）

只有 owner（或 owner 的员工）能进后台。三种角色：

| 能力                            | 超级管理员 `admin` | 可修改用户 `operator` | 一般用户 `viewer` |
| ----------------------------- | :-----------: | :--------------: | :-----------: |
| 查看节点 / 持仓 / 告警 / 拓扑           |       ✅       |         ✅        |       ✅       |
| **修改 receiver 配置**            |       ✅       |         ✅        |       ❌       |
| 下发命令（pause / resume / reload） |       ✅       |         ✅        |       ❌       |
| 增加 / 停用使用者                    |       ✅       |         ❌        |       ❌       |
| 管理 IP 白名单 / 节点 token          |       ✅       |         ❌        |       ❌       |
| 查看审计日志                        |       ✅       |         ❌        |       ❌       |
| 回滚配置版本                        |       ✅       |         ✅        |       ❌       |

**实现要点**：

- 口令用 **argon2**（不是 SHA/MD5）—— **实现偏差（2026-10-14）**：本工具链无
  `sha2`/`bcrypt`/`argon2` crate 可用，实际实现为**纯 Rust SHA-256 加盐迭代哈希**
  （`users.rs` 的 `hash_password`，16 字节盐 + 迭代；FIPS 向量测试在档）。
  复用时优先换回 argon2，届时 `users.json` 里的存量哈希需要一次性迁移
- 会话用 **HttpOnly + SameSite=Lax Cookie**（不用 localStorage JWT——XSS 能偷）
- **登录失败退避**（防爆破）
- **新用户默认 `viewer`**：加权限是一个**显式动作**，不是默认值。
    
  默认给 `operator` 会让"加个人来看看"变成"加个人能改配置"
- 审计里记 `actor`——**每一次配置变更都能回答"是谁改的"**
- 第一版不做自助注册：**用户只能由 `admin` 创建**（符合"只有 owner 和员工能进"）

> **✅ 已澄清（D12）：是多用户，不是多租户。**
>
> 一个 owner（或 owner 的员工）共用同一套 Hub，彼此之间**没有隔离需求**。
>   
> 所以只需要 `user ID + 密码 + 用户等级`，**不做租户隔离**。
>
> 数据模型里**也不需要 `tenant_id`**——多租户那套（每张表加 `tenant_id`、
>   
> 每条查询按它过滤、每个资源都要校验归属）在只有**一个 owner** 的前提下，
>   
> 是纯粹的复杂度，不带来任何收益。
>
> 真要变成多租户的那一天，那是**一次架构变更**，不是"当初少加了一列"。

## 19. 安全

中枢把"能改所有 receiver 配置"集中到一处，**因此成为整个系统最有价值的攻击目标**。

| 层    | 措施                                       |
| ---- | ---------------------------------------- |
| Web  | TLS；反向代理限流；HSTS/CSP                      |
| 认证   | 本地用户（实现为 SHA-256 加盐迭代哈希，见 §17.2 偏差说明；目标 argon2）+ 可选 OIDC；登录失败退避             |
| 授权   | `viewer` / `operator` / `admin`；**默认只读** |
| ZMQ  | **CURVE 必须开启**（Tier 2 链路）                |
| 节点认证 | **建议保留一个轻量 token**，理由见下                  |
| 危险操作 | magic 变更二次确认 + 角色检查 + 审计（§10）            |
| 审计   | 所有写操作 append-only，含操作人 IP、前后值、结果         |

### ✅ 19.1 已决定：只走防火墙 IP 白名单（单端口、无 token）

| 层   | 机制                                         |
| --- | ------------------------------------------ |
| 网络层 | **Hub 只开一个端口**，防火墙/云安全组只放行白名单来源，名单外**连不上** |
| 应用层 | **无 token**。能连上 = 被信任                      |


Hub 因此**不需要任何对端 IP 判断**——ZMQ 不直接暴露对端 IP，
  
而这个方案把这道判断整个挪到了防火墙层，**连接建立前就拒掉**，
  
Hub 连扫描流量都看不到。**这是最干净的实现方式。**

#### 这个选择带来一条运维要求（必须提前知道）

> **每个节点的"出口 IP"必须是固定的，否则加不进白名单。**

注意是**出口 IP**，不是"有没有公网 IP"：一台在 NAT 后面的机器主动连出来，
  
Hub 看到的是 NAT 的公网地址——**只要那个地址不变，就能加白名单**。
  
会出问题的是**动态 IP**（家宽、4G/5G、部分云主机的浮动出口）。

**如果确实有节点的出口 IP 会变，推荐用 WireGuard（或任何 VPN）而不是回到 token：**

- 所有节点先连 VPN，各自拿到一个**固定的 VPN 地址**（如 `10.8.0.11`）
- Hub 只监听 VPN 网段，防火墙只放行 `10.8.0.0/24`
- **每台机器的地址从此固定**，与它真实的网络环境无关
- 顺带获得：链路加密、不暴露公网端口

这比"加 token"更彻底，而且**不需要改一行 Hub 或 EA 代码**——
  
它只是在"白名单"这个方案里，把"地址"这件事解决了。

#### 需要明确知道的唯一后果

这个方案**没有第二层**。任何能连上 6000 端口的机器：

- 订阅 `\x01` 就能**读到所有 sender 的完整持仓快照**（品种、手数、SL/TP）
- 伪造 `ROLE=sender` + 一个账号，就能**往别人的 receiver 推假数据**

因此**白名单本身成了唯一的信任边界**，必须：

- 名单尽可能短，只放真实节点
- 云安全组 / 防火墙规则**纳入变更审计**（谁能改、改了什么）
- 别把 6000 端口暴露给 `0.0.0.0/0`——那等于没有白名单

> **CURVE 已实现（2026-10-15）**：`--curve on` 让中枢成为 CURVE 服务端——链路加密，
> 且每个节点必须出示在**允许名单**（`curve_clients.txt`，每行一个 40 字符 Z85 公钥）
> 内的密钥对。名单由 **ZAP 处理器**（RFC 27）在**握手阶段**执行：这是 libzmq 唯一
> 「问应用、并照办」的地方，因此不在名单上的订阅者**根本建立不了连接**——若只在收包
> 处检查，中枢挡得住伪造数据，却挡不住别人**读到全部持仓流**（发布是 libzmq 的活，
> 不是应用的）。空名单 + `--curve on` 会**拒绝启动**；唯一表示「任何密钥对都行」的
> 写法是单独一行 `*`。它是**链路层**的，不改变上面 §19.1 的结论（防火墙仍是网络层
> 边界），但把「能连上 6000 就能读到所有持仓」从风险清单里拿掉了。
> **两侧默认均已打开**（2026-10-15 owner 定的测试期设置）：**中枢**默认 `--curve on`；
> **EA 侧** 中枢链路 CURVE **硬编码 ON**（原 `HubUseCurve` input 已删除，改为
> `const bool HubUseCurve = true`），且 **`HubPublicKey` input 也已删除**
> （2026-10-16）：公钥从**文件**读取——`MQL<4|5>\Files\copier_hub.key`，回退
> `Terminal\Common\Files`（一个文件服务本机所有终端）。两种取法：
> dashboard 的 **⬇️ Download Key File** 按钮（即 `GET /api/v1/curve/hub_key`），
> 或手工把 hub banner 里的公钥写进该文件。**顺序仍不能颠倒**（重挂节点前，中枢必须已在
> CURVE 状态），但引导期不再需要抄 40 字符公钥：`--curve-learn on` 让中枢接受任何已认证
> 密钥对，并**自动把节点公钥追加进允许名单文件**（标 `# learned`，删行即撤销）；全部节点
> 接入一次后，去掉 learn 重启即为强制名单。learn 是**信任首次使用**（TOFU），属引导工具
> 而非常态，端口防火墙仍然重要。密钥轮换（G15）仍是手工流程。

> 这一条不是流程洁癖：**能读到持仓快照 = 能提前知道别人在做什么单。**

## 21. 风险与对策

| #      | 风险                           | 影响                 | 对策                                                                                                                              |
| ------ | ---------------------------- | ------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| **R1** | 中枢是交易路径单点                    | 中枢挂 → receiver 停收  | ① 无状态转发，重启即恢复；② **快照是全量替换**，宕机期间只是"镜像冻结"；③ receiver 的**喂价停滞闸门**（已实现）主动拦新单；④ **中枢不在时 receiver 用本地 ini 继续跑**（§7.3）；⑤ systemd 自动重启 |
| **R2** | sender 同时连两条通道，receiver 收到两份 | 重复执行               | 两条通道上 `SID`/`SSID` **不同**（账号 vs 端口），所以是两条独立流；但若一个 receiver 同时连中枢与直连同一 sender，会得到**两份语义相同的流**。→ 配置上强制**二选一**，并在启动时检测告警           |
| **R3** | 中枢重启导致 receiver 误判 sender 重启 | 反复重新同步             | **原样透传 `SSID`**，中枢绝不重写                                                                                                          |
| **R4** | 主题前缀碰撞（账号互为前缀）               | 收到别人的数据            | `@` 分隔控制/数据命名空间（§4.4）；数据侧账号等长时不会碰撞；§6.1 的 `ROLE:ACC` 作为内部 ID                                                                    |
| **R5** | MT4 magic 溢出（§6.2）           | 算出一个错的 magic → 孤儿化 | **已定案**：确定性截断为 9 位 + 启动 warning；碰撞由现有"重复 magic 即拒绝启动"兜住                                                                         |
| **R6** | 多帧在 mql-zmq 上未验证             | 方案 B 可能不成立         | **开工第一步写探针测试**（§4.3）；万一不可用则降级方案 A                                                                                               |
| **R7** | 中枢被未授权节点接入                   | 持仓泄漏 / 假数据注入       | **已定案**：防火墙层 IP 白名单 + **名单外必须持 token**（§19.1）                                                                                   |
| **R8** | 主备配置库双写                      | 配置互相覆盖             | 配置库单写（§11.2）                                                                                                                    |
| **R9** | 中枢自身 bug 污染交易数据              | 最严重                | **只转发两帧、Frame 1 一字节不碰**（§3.2），从架构上消除这类风险                                                                                        |

> **R1 是决定"能不能做"的那一条。** 它可接受，完全建立在"快照=权威全量状态"上。
>   
> **如果哪天改成增量协议，中枢就不再可以宕机了。**
>
> **R6 是决定"方案 B 能不能做"的那一条。** 所以它排在实施第一步。

>
> 修复见 `hub/build.sh` 第 2 节：vendor 了 `third_party/binutils/`（只含
> `as`/`ar`/`dlltool` 三个工具），且 **PATH 顺序是承重墙** ——
> 必须排在 Rust `self-contained` **之前**。放反了、或把整个 mingw64 树提前，
> hub 会以 `ld: cannot find crt2.o` 失败（那样会连带抢走 Rust 的 `ld`/`gcc`）。
> 详见 `hub/README.md` 末尾「A build note for what comes next」。
