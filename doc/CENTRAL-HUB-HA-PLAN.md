# mt-copier 主备 Hub 双机热备设计方案书
## 核心模式：双端双活连接（Active-Active Dual-Connected Model）

> **状态**：方案已选定（方案 A），待团队评审确认  
> **修订日期**：2026-10-26  
> **适用版本**：mt-copier v1.0+ (MQL4/MQL5 + Rust Hub)  
> **目标**：消除单点故障（SPOF），实现毫秒级甚至零感知的无缝故障转移，保障跟单系统 7×24 小时不间断运行。

---

## 1. 方案背景与架构选型结论

在量化交易与多账户跟单系统中，中央中枢（Hub）是所有信号分发与监控的核心。若 Hub 仅有单点实例，一旦遭遇物理机断电、操作系统网络抖动、维护升级或进程意外中断，跟单系统将出现信号丢失甚至无法平仓的巨大风控风险。

针对主备高可用，前期评估了两种方案：
- **方案 A（已采纳）：双端双活连接（Active-Active Dual-Connected）**：Sender 与 Receiver 同时连接主备两台 Hub；主备两端对齐数据流；依靠协议层天然的 `SEQ` 序列号与 `UID` 幂等守卫自动消除重复帧。
- **方案 B（放弃）：主备热切换（Hot-Standby Failover）**：Sender 双推，Receiver 平时仅连主，主断线经检测超时（3~10秒）后切至备。

### 为什么坚决选定方案 A？
1. **0 毫秒切换窗口**：方案 B 存在不可避免的 TCP 断线超时判定（通常需 3~5 秒），在此窗口内发生的极速开平仓信号会彻底丢失；而方案 A 两路管道时刻通畅，主 Hub 宕机的**同一毫秒**内，备 Hub 的数据包早已到达，**零延迟、零丢单**。
2. **协议天然幂等，绝无重开仓风险**：跟单协议具备 `SID:SSID:SEQ` 唯一序列单调递增守卫，且本地执行引擎具备 `CopierSeenRing`（`g_seen`）开仓去重。双份一模一样的指令到达，第二份被底层微秒级丢弃，无任何副作用。
3. **客户端状态机极简，杜绝隐蔽 Bug**：不需要在 MQL 客户端编写复杂的“超时检测、虚假抖动判定、降级重试、回切主节点”等状态机，从根源上消除了客户端因网络不稳定导致的逻辑死锁。

## 3. 核心机制详解

### 3.1 单地址填入与自动集群拓扑下发

#### 需求痛点
交易员在 MT4/MT5 客户端设置参数时，输入过长或带有符号的地址（如 `1.2.3.4:6000,1.2.3.4:6001`）极易产生拼写错误（如混入中文逗号、前导空格）。

#### 解决方案与通信交互
1. **输入极简**：EA 的属性参数 `HubEndpoint` 仅需填写**任意一个可达的 Hub 地址**（通常是主 Hub 地址，如 `10.8.0.1:6000`）。
2. **上线通告**：客户端启动后，向该地址建立 XSUB 连接，并发送初始握手包：
   ```text
   V=1|SID=...|SSID=...|SEQ=1|TS=...|MS=...|T=REG|P=ROLE=receiver;ACC=123456;...
   ```
3. **拓扑回传**：无论是主 Hub 还是备 Hub，收到 `REG` 后，立即单播回复一条集群拓扑包（`T=TOPOLOGY`）：
   ```text
   V=1|SID=hub|SSID=hubproto|SEQ=...|T=TOPOLOGY|P=PRIMARY=10.8.0.1:6000;STANDBY=10.8.0.2:6001;ACTIVE=primary
   ```
4. **客户端感知并双连**：
   - EA 解析出 `PRIMARY` 与 `STANDBY` 两个地址；
   - 现有的 XSUB 套接字调用 `m_sub.connect(standby_ep)` 建立第二条下行/上行流；
   - 客户端此时进入**双活接入状态**。

### 3.2 客户端本地磁盘持久化防死锁机制（关键容灾防线）

必须杜绝“内存态缓存失效导致无法启动”的隐患：

```
                 客户端启动 (OnInit)
                         │
                         ▼
             检查 HubEndpoint 是否可连通？
                   /           \
             (是) /             \ (否：主 Hub 此时可能已宕机)
                 ▼               ▼
           正常连通主 Hub       读取本地 MQL\Files\copier_hub_cluster.st
                 │               │
                 ▼               ▼
           接收 TOPOLOGY     提取历史缓存的备用 Hub 地址并发起连接
                 │               │
                 ▼               ▼
           更新写入磁盘 ◄────────┴────── 成功联通备 Hub，正常跟单自愈！
```

* **磁盘缓存文件**：`MQL\Files\copier_hub_cluster.st`
* **格式内容**：
  ```ini
  primary=tcp://10.8.0.1:6000
  standby=tcp://10.8.0.2:6001
  updated=1771900800
  ```
* **自愈闭环**：即便主 Hub 彻底烧毁下线，后续重启 MT4 终端，EA 在输入框的主地址连不上时，自动读取本地缓存的 `standby` 地址建立通信，集群永不失联。

### 3.3 零重复开仓的技术铁律：双活幂等证明

在双活模式下，Sender 的同一笔订单（如 `OPEN EURUSD Buy 1.00`）会同时通过 Primary Hub 和 Standby Hub 转发至 Receiver。Receiver 会不会开出两笔仓位（双倍手数）？

**答案：绝对不会。系统有三层硬件级安全过滤防线**：

```
[来自 Primary Hub]  OPEN SEQ=100 UID=ABC1234567 ──┐
                                                  ├──► [ Receiver 进站网关 ]
[来自 Standby Hub]  OPEN SEQ=100 UID=ABC1234567 ──┘           │
                                                              ▼
                                                   第一防线: SEQ 序列号守卫
                                                   (SEQ <= last_seq 直接丢弃)
                                                              │
                                                              ▼ (若极微小并发同时越过)
                                                   第二防线: CopierSeenRing (g_seen)
                                                   (已开仓 UID 环形表瞬时去重)
                                                              │
                                                              ▼
                                                   第三防线: Local Position Comment
                                                   ("tc|ABC1234567" 唯一注释防线)
```

1. **第一层：`SEQ` 单调递增序列号守卫**  
   Sender 在生成事件时分配单调递增的 `SEQ`。Receiver 在处理时维护 `last_seq`。先到的第一帧被处理，后到的第二帧因 `SEQ <= last_seq` 在网关处被微秒级丢弃。
2. **第二层：`CopierSeenRing`（`g_seen`）动作环形去重**  
   在进入交易队列前，系统基于 `key = sender_id + ":" + kind + ":" + uid` 校验 `g_seen.Has(key)`。若已执行过开仓，第二笔被判定为完全重复指令直接压制。
3. **第三层：本地订单注释与 UID 唯一映射**  
   Receiver 实际发单时携带 `tc|<UID>|<Ticket>`。即便在极端异常状态下，本地持仓对齐（Converge）逻辑也会判定该 UID 的持仓已存在，决不会开出第二张单。

### 3.4 CURVE 加密体系：相同服务端 Key 铁律

#### 底层限制与原理
在 ZeroMQ 官方设计中，**一个 XSUB Socket 上只能通过 `zmq_setsockopt(ZMQ_CURVE_SERVERKEY)` 绑定一个 32 字节的服务端公钥**。若主备 Hub 使用不同的密钥对：
- 客户端同一个套接字无法同时加密连接两台 Hub；
- 切换时必须销毁重构 Socket 上下文，造成明显的延迟与资源泄漏风险。

#### 统一设计规范
1. **密钥共享**：Primary Hub 与 Standby Hub **必须配置完全相同的 `curve_hub.keys`**（包含相同的公钥与私钥）。
2. **客户端体验**：
   - 客户只需从 Web UI 下载一次 `copier_hub.key`（或部署时分发一次）；
   - EA 加载该公钥后，同一个 `m_sub` 可以同时向 `6000` 和 `6001` 发起 CURVE 安全握手，两边均能瞬间握手成功。
3. **授权白名单同步**：客户端的公钥（`curve_clients.txt`）会在主备 Hub 之间自动实时同步，新节点在任一边上线均能被两端信任。

### 3.5 快照收据中继（`RCPT`）的双向消抖闭环

在中央模式下，Receiver 的快照接收凭证（`H=<hash>`）承载于 `STAT` 消息上报给 Hub，Hub 解码后作为 `RCPT` 消息单播回传给 Sender：
1. **双份收据到达 Sender**：主 Hub 和备 Hub 都会向 Sender 回传 `RCPT`。
2. **幂等安全性**：检查 `CopierSender.mq4` 源码，Sender 收到 `RCPT` 仅将其写入 `g_recentSnapHashes` 环形缓冲，并更新对端最新确认的 `g_snapHash`。由于两份收据内容完全相同，重复确认只刷新时间戳，**不会触发任何错误的快照补发风暴**。

## 4. 主备 Hub 间的数据状态同步（Replication Engine）

### 4.1 数据同步分类与边界明确

不是所有数据都需要在主备之间复制，清晰的边界划分能让系统保持极简、坚固：

| 数据类型 | 文件 / 载体 | 是否需要主备同步？ | 同步机制与理由 |
| :--- | :--- | :---: | :--- |
| **Web 用户认证** | `users.json` | **必须同步** | 保证管理员/操作员账号、角色与密码哈希两端一致。 |
| **管控与暂停状态** | 运行态 Paused / `commands.jsonl` | **必须同步** | 保证主节点执行的“全局暂停/单节点暂停/平仓”在备机具有相同效力。 |
| **配置修订版本历史** | `config_revisions.jsonl` | **必须同步** | 保持递增的 `REV` 版本一致，防止备机下发低版本配置被客户端拒绝。 |
| **CURVE 客户端白名单** | `curve_clients.txt` | **必须同步** | 保证新授权的客户端在主备两端都能顺利通过 CURVE 认证。 |
| **系统告警通道** | `alert_channels.json` | **必须同步** | 微信/邮件告警通道配置在故障接管后依然有效生效。 |
| **客户端 INI 配置内容** | `copier.ini` 实际内容 | **无需双向同步** | **客户端是唯一真实态**。客户端连上备 Hub 发送 `REG`（带 `IH` 哈希），备 Hub 若无此哈希则通过 `reqcfg` 自动从客户端拉取最新生效 INI。 |
| **订单快照与持仓监控** | 内存持仓字典 | **无需同步** | Sender 与 Receiver 双推数据，两台 Hub 的内存快照各自实时独立生成，状态自然一致。 |

---

### 4.2 主备间同步协议（Inter-Hub Sync Protocol）

主备之间通过轻量级 HTTP/WebSocket 通信（或专用 TCP 同步端口）：
1. **心跳探针（1 秒/次）**：
   - Standby Hub 定期向 Primary Hub 发起心跳探针：`GET /api/v1/cluster/ping`
   - 返回 Primary 的当前集群状态：`{ "role": "primary", "users_rev": 12, "cfg_rev": 45, "paused": false }`
2. **增量/全量同步触发**：
   - 当检测到 Primary 的配置版本或用户版本大于 Standby，Standby 自动发起拉取请求：
     - `POST /api/v1/cluster/sync`
     - 同步内容为变更的 JSON 记录，写入本地文件并重载。
3. **断网与分区处理**：
   - 当心跳连续 3 次超时（3 秒无响应），Standby 判定 Primary 离线，并在监控面板提示警告。

### 4.3 Web UI 防脑裂操作机制（Active-Passive Operator Controls）

虽然数据层面双活，但**人的操作（Web Dashboard）必须保持逻辑单一**，防止两位管理员在两边同时做冲突修改：

1. **界面状态标识**：
   - Primary Hub (6010)：页面顶部显示绿色徽章 **`[PRIMARY 主节点 - 读写激活]`**。
   - Standby Hub (6011)：页面顶部显示橙色醒目标签 **`[STANDBY 备用节点 - 只读镜像]`**。
2. **只读保护与手动提权（Promote）**：
   - 平时 Standby Hub 的修改配置、下发命令按钮处于禁用状态，并提示：“请在主节点操作；若主节点已故障，请点击「接管为主节点」”。
   - 当主节点确认失联时，操作员在 6011 点击 **`⚡ Promote to Primary (接管为主节点)`**，Standby 升级为 Primary 接受写操作，并记录审计日志。

## 5. 故障演练与容灾矩阵（Failure Scenarios）

| 故障场景 | 故障现象 | 系统响应与自动自愈逻辑 | 交易业务影响 |
| :--- | :--- | :--- | :---: |
| **场景 1：主 Hub 物理断电 / Crash** | 6000/6010 瞬间无法连通 | Sender/Receiver 的备用通道（6001）早处于就绪状态，数据流毫无停顿地继续传输。Standby Hub 检测到对端失联，报警通知。 | **0 毫秒感知<br>0 笔漏单** |
| **场景 2：备 Hub 维护重启 / 宕机** | 6001 无法连通 | 主链路（6000）全速运行，不受任何影响。EA 端打印单条备路重连警告，不打扰交易。备 Hub 恢复后自动重连主 Hub 同步数据。 | **零影响** |
| **场景 3：主备间网络分区（脑裂风险）** | 主备之间无法互访，但两端均能连通外网 | 数据通道：Sender 依旧向两边发送，Receiver 依旧正常接收去重；管理通道：两端各自保持当前状态，等待运维人工接入仲裁。 | **交易零影响<br>管控锁定** |
| **场景 4：客户端重启且主 Hub 故障** | 主 Hub 已死，终端重启 | EA 初始化时尝试连接输入框的主 Hub 失败；自动回退读取本地 `copier_hub_cluster.st` 缓存，直接连通备 Hub 顺利上线。 | **自愈恢复<br>顺利跟单** |
| **场景 5：主 Hub 修复重启上线** | 主 Hub 重新开机启动 | 主 Hub 发送 `@all WHO`，各 EA 重新发送 `REG`；主 Hub 通过客户端报文快速重建内存注册表；主备重新握手同步状态。 | **全自动对齐** |
